# 要件定義書

状態: **Draft**（設計段階。実装・実機検証は未実施）

## 1. 目的と背景

[AWS 版テンプレート](https://github.com/naoya03708/aws-terraform-web-template)に続き、Google Cloud 上の Web アプリ向けインフラを、Terraform / Terragrunt で再利用できるテンプレートとして提供する。

- 「構成を書ける」だけでなく、**運用（SLO ベースの監視、CI/CD、設計判断の記録、コスト）まで含めて任せられる**ことを示す。
- AWS 版で得た知見（実機検証で見つかった不具合、組織の統制による制約）を設計に反映する。

### 想定する読み手
- テンプレートを使う開発者・SRE
- ポートフォリオとして内容を評価する人（案件の発注側、面談官）

## 2. スコープ

| 区分 | 内容 |
| --- | --- |
| 含む | IaC（Terraform / Terragrunt）、CI/CD、SLO ベースの監視、設計記録（ADR）、コスト試算、実機検証 |
| 含む（段階分け） | **第1段階: Cloud Run**、**第2段階: GKE Autopilot**（別モジュールとして追加） |
| 含まない | アプリ本体（サンプルのコンテナイメージを使う）、マルチリージョン構成、独自ドメインの取得・DNS 運用、CMEK（将来の拡張） |

## 3. 機能要件

| ID | 要件 | 段階 |
| --- | --- | --- |
| F-01 | コンテナ化した Web アプリを公開できる（`container_image` で差し替え可能） | 1 |
| F-02 | HTTPS で到達できる。独自ドメインが無い場合は Cloud Run の `*.run.app`（Google 管理の証明書）を使う | 1 |
| F-03 | リレーショナル DB（PostgreSQL）を、インターネットに公開せずアプリから使える | 1 |
| F-04 | DB のパスワード等の秘密情報を、コード・変数・ログに平文で残さずアプリに渡せる | 1 |
| F-05 | dev / prod の環境を、同じコードで、変数の差分だけで構築できる | 1 |
| F-06 | 負荷に応じて自動でスケールする（上限・下限を変数で指定できる） | 1 |
| F-07 | 外部 HTTPS ロードバランサ + WAF（Cloud Armor）を、任意機能（フラグ）として有効化できる | 1 |
| F-08 | SLO に基づくアラームと、ダッシュボード、通知（緊急 / チケット）を提供する | 1 |
| F-09 | コンピュートを GKE Autopilot に切り替えて（または追加して）使える。ネットワーク・DB・監視は共有する | 2 |

## 4. 非機能要件

### 4.1 可用性・性能（仮の SLO）
サンプルアプリ向けの仮値。実サービスでは、ユーザーと合意した値に置き換える。AWS 版と同じ値にして、比較しやすくする。

| 項目 | SLO（仮） |
| --- | --- |
| 可用性 | 99.5%（30日） |
| レイテンシ | p95 500ms 未満 |

### 4.2 セキュリティ
- 長期のサービスアカウントキーを作らない。ローカルは ADC（`gcloud auth application-default login`）、CI は Workload Identity Federation を使う。
- plan 用と apply 用でサービスアカウントを分け、plan 用は閲覧権限のみにする。信頼条件は本リポジトリと GitHub Environment に限定する。
- DB は private IP のみ。DB 認証情報は Secret Manager で管理する。
- 公開リポジトリのため、プロジェクト ID、アカウント情報、メールアドレスをコード・ドキュメント・コミットに含めない。

### 4.3 運用性
- アラームは「ユーザーが困っているか」だけを鳴らす（原因系メトリクスはダッシュボードのみ。例外は DB のディスク逼迫）。
- アラームごとの意味と一次対応を `docs/slo.md` に書く（runbook）。

### 4.4 コスト
- dev は検証時のみ起動し、検証後は `destroy` する。
- 費用の見積もりと、実機検証での実績を `docs/cost.md` に記録する。

### 4.5 再現性・保守性
- Terraform / プロバイダ / devcontainer のバージョンを固定し、lock ファイルをコミットする。
- 設計判断は ADR に、理由とトレードオフを含めて残す。

## 5. 制約・前提

| 項目 | 内容 |
| --- | --- |
| 検証環境 | Google Cloud の無料トライアル（$300 / 90 日）。個人の Google アカウント。**Google が自動で作成した組織（Organization）の配下**にプロジェクトを作る（組織レベルの Org Policy が効く。確認結果は ADR 0006） |
| リージョン | 東京（`asia-northeast1`） |
| ドメイン | 無し。HTTPS の確認は `*.run.app`。外部 LB（任意機能）は、ドメイン無しの検証では使わない |
| 通知先 | 検証用に個人のメール。**リポジトリには書かず**、実行時に環境変数で渡す |
| 公開範囲 | 公開リポジトリ。実機検証していない範囲は、README に明記する |

## 6. 受け入れ基準

| # | 基準 | 確認方法 |
| --- | --- | --- |
| 1 | CI（fmt / validate / lint / セキュリティスキャン / `terraform test`）が通る | GitHub Actions |
| 2 | dev を実環境に apply でき、HTTPS で応答する | 実機検証 |
| 3 | 擬似障害でバーンレートのアラームが発火し、復旧で戻る | 実機検証 |
| 4 | ダッシュボードの SLO タイルが、障害を反映する | 実機検証（AWS 版で、実機でしか見つからない不具合があった） |
| 5 | `destroy` 後に、課金リソースが残っていない | CLI で確認 |
| 6 | 検証していない範囲が、README に明記されている | レビュー |

## 7. AWS 版から引き継ぐ教訓

| AWS 版で起きたこと | GCP 版への反映 |
| --- | --- |
| ダッシュボードの 30 日タイルが、障害中も 100% を表示（期間の指定漏れ） | 受け入れ基準 4 を設け、実機で確認する。SLO は Cloud Monitoring のネイティブな SLO を使い、自前の計算式を減らす |
| 組織の SCP が OIDC プロバイダの作成を拒否し、CI 認証が未検証に | 検証前に、組織・プロジェクトの Org Policy を確認する（実施済み。設計を止める制約は無かった）。拒否された場合の記録方法も決めておく |
| `destroy` で消えないリソース（Container Insights のログのグループ）が残った | `destroy` 後の残存確認の対象に、ログのグループ、Artifact Registry、Secret Manager、ログ バケットを含める |
| 稼働時間を測っておらず、コストの精度の裏付けが粗くなった | apply / destroy の時刻を記録し、課金の内訳を確認する |
| ローカルと CI の lock ファイルが食い違うおそれ | 複数プラットフォームのハッシュを入れて、最初からコミットする |
