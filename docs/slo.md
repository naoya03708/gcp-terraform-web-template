# SLO とアラームの runbook

状態: **実装済み・実機未検証**（SLO のフィルタ、バーンレートのアラート、ダッシュボードは、フェーズ 3 の実機検証で確認する）。

## 方針
- アラームは「ユーザーが困っているか」だけを鳴らす。CPU・メモリなどの原因系はダッシュボードで見るだけにする。
- 例外は **Cloud SQL のディスク使用率**（自動拡張が追いつかなくなる前に気づくため）。
- 緊急（page）とチケット（ticket）は、通知チャネルを分ける。

## SLO（仮の値。サンプルアプリ向け）

| 項目 | SLI | 目標 | 期間 |
| --- | --- | --- | --- |
| 可用性 | 全リクエストのうち 5xx 以外の割合（4xx は良とみなす） | 99.5% | 30日（ローリング） |
| レイテンシ | 閾値（500ms）以内で応答したリクエストの割合 | 95% | 30日（ローリング） |

- Cloud Run は Cloud Monitoring が自動検出するサービスではないため、`google_monitoring_custom_service` を作り、`run.googleapis.com/request_count` と `request_latencies` から SLI を定義している。
- Cloud Monitoring の SLO は、目標の上限が 0.999、期間の上限が 30 日。

### AWS 版との違い（ADR 0003）
- AWS 版のレイテンシは「**p95 が 500ms 未満**」の閾値アラーム。GCP 版は、SLO の SLI として「**500ms 以内のリクエストが 95% 以上**」を使う。
- 両者は近いが同じではない（p95 < 500ms ⇔ 95% のリクエストが 500ms 未満、は分布上ほぼ等価だが、集計の方法が違う）。AWS 版と数値を並べて比較するときは、この違いに注意する。

## バーンレートのアラート

エラーバジェットの消費の速さ（バーンレート）を、長い窓と短い窓の両方が超えたときに鳴らす（multi-window multi-burn-rate）。短い窓を AND で足すのは、すでに収まった障害で鳴り続けないため。

| アラート | 通知 | 条件 | 意味（30 日の予算を使い切るまで） |
| --- | --- | --- | --- |
| availability fast burn / latency fast burn | page | 14.4 倍（1h ∧ 5m） | 約 2 日 |
| availability slow burn / latency slow burn | ticket | 6 倍（6h ∧ 30m） | 約 5 日 |

> **未検証**: 1 つのポリシーに、窓の違う 2 条件を `combiner = "AND"` で入れる書き方は、公式の例にない。provider の仕様上は可能だが、実際に発火・復旧するかは、フェーズ 3 の擬似障害で確認する。

## 一次対応

### availability fast burn（page）
1. ダッシュボードの「Requests by response class」で、5xx の増加を確認する。
2. 直近のデプロイ（Cloud Run のリビジョン）の有無を確認する。原因が直近のデプロイなら、前のリビジョンにトラフィックを戻す。
3. Cloud Run のログ（`severity>=ERROR`）で、エラーの内容を確認する。
4. DB 接続の失敗が多い場合は、Cloud SQL の状態（ダッシュボードのディスク使用率、インスタンスの状態）を確認する。

### availability slow burn（ticket）
1. エラーが出ているパス・リビジョンを、ログから特定する。
2. 営業時間内に、原因の修正をチケットとして起票する。バジェットの残りをダッシュボードで確認し、残りが少なければ、機能リリースを止めて信頼性の改善を優先する。

### latency fast burn（page）
1. ダッシュボードの「Request latency p95」と「Cloud Run instance count」を確認する。
2. インスタンス数が上限（`run_max_instances`）に張り付いていれば、上限を引き上げる。
3. コールドスタートが原因の場合は、`run_min_instances` を 1 以上にする（prod の既定は 1）。
4. DB のクエリが遅い場合は、Cloud SQL のメトリクスとログを確認する。

### latency slow burn（ticket）
遅いパスをログ・トレースから特定し、改善をチケットとして起票する。

### DB disk（ticket）
Cloud SQL のディスク使用率が 85% を超えた。自動拡張が有効でも、上限に達する前に、不要なデータの削除またはディスクサイズの見直し（`db_disk_size_gb`）を検討する。

## 簡略化した点
- SLI は Cloud Run のリクエスト単位（フロントの外形監視ではない）。Cloud Run に到達する前の失敗（DNS、LB など）は測れない。
- 通知は、検証用に、緊急とチケットで同じ宛先にしている（チャネルは分けてある）。実運用では、緊急をオンコール用の通知（PagerDuty など）に差し替える。
- 4xx は良いリクエストとして数える。認証の不具合などで 4xx が急増しても、可用性のアラートは鳴らない。

## 実機で確認すること（フェーズ 3）
- SLO のフィルタが、実際のメトリクスを拾えているか（`response_code_class` の値、`request_latencies` の単位）。
- 長窓 ∧ 短窓の AND のポリシーが、擬似障害で発火し、復旧で戻るか。
- ダッシュボードの各タイルが、障害を反映するか（AWS 版では、実機でしか見つからない不具合があった）。
- 擬似障害の方法: サンプルイメージ（hello）は 5xx を返せない。存在しないリビジョンの指定や、起動に失敗するイメージの差し替えなど、実機で方法を決める。
