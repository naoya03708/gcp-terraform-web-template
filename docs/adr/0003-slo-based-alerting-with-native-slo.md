# 0003. アラームは SLO ベースにし、Cloud Monitoring のネイティブな SLO を使う

状態: Accepted（SLO のフィルタ、AND 条件のバーンレートのアラート、ダッシュボードの数値は、実機で確認済み。画面の見た目は未確認）

## 背景
CPU やメモリの閾値アラームは、ユーザー影響と一致せず、誤報と通知疲れを招く。AWS 版では、「ユーザーが困っているか」だけを鳴らす設計にし、メトリクス計算式でバーンレートを自前実装した（AWS 版 ADR 0003）。実機検証では、ダッシュボードのタイルの期間指定で不具合が見つかった。

## 決定
- アラームは SLO ベースにする。原因系メトリクス（CPU・メモリ等）は、ダッシュボードのみ。例外は Cloud SQL のディスク逼迫。
- SLO は、Cloud Monitoring の SLO（`google_monitoring_slo`）で定義する。アラームは、SLO のバーンレートの条件で作る。
- バーンレートは、長窓と短窓の AND（緊急: 14.4 倍 / 1h と 5m、チケット: 6 倍 / 6h と 30m）。AWS 版と同じ閾値にして、比較できるようにする。
- 通知チャネルは、緊急用とチケット用に分ける。
- SLO の値は仮値で、変数で調整できるようにする。可用性は 99.5%（30 日）、レイテンシは「**500ms 以内のリクエストが 95%**」。
- Cloud Run は自動検出のサービスではないため、`google_monitoring_custom_service` を作り、`run.googleapis.com/request_count`（可用性: 5xx を bad、全件を total）と `request_latencies`（レイテンシ: 分布の `distribution_cut`）から、リクエストベースの SLI を定義する。

## 理由
- ネイティブの SLO を使うと、SLI の集計とバーンレートの計算を、自前で組まなくて済み、計算式の誤りを減らせる。
- AWS 版と同じ設計思想なので、2つのテンプレートで、運用の考え方を揃えられる。

## トレードオフ
- ネイティブの SLO には制約がある。目標の上限は 0.999、評価期間の上限は 30 日。
- **AWS 版との SLI の違い**: AWS 版のレイテンシは「p95 が 500ms 未満」の閾値アラーム。GCP 版は「500ms 以内が 95%」の SLO。近いが同じではなく、AWS 版と数値を並べるときは注意が要る（`docs/slo.md`）。
- **実機で確認済み**（2026-11-24）: 長窓と短窓の AND（`combiner = "AND"` で 1 ポリシーに 2 条件）は、公式の例にない書き方だったが、擬似障害で、**発火（注入の約 5 分後）も、解決（短窓が外れたとき。長窓が高いままでも閉じた）も、期待どおり**だった。fast burn の解決は、最後の 5xx から約 14 分後（想定の約 5 分より長い。復旧中にトラフィックが途切れ、短窓にデータが無かったことなどが考えられるが、原因は未確認）、slow burn は約 33 分後（30m の窓に一致）。
- バーンレートのフィルタ文字列は、SLO の name が apply 後に確定するため、plan のテストでは検証できない（実機で確認済み）。
- 通知の件名には、ポリシー名ではなく条件名が出る。緊急とチケットを見分けるため、条件名に `[page]` / `[ticket]` を付け、`severity`（緊急: CRITICAL、チケット: WARNING）を設定した。
- ダッシュボードのタイルは、ネイティブ機能ではなく、単体テストでも検証できないため、実機で障害時の表示を必ず確認する（受け入れ基準 4）。
